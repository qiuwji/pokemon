# 宝可梦跟随插件与通用 Actor 能力：调研评审稿

日期：2026-10-07。状态：通用能力改进已获实现授权并进入验证；尚未实现或验证跟随功能。依据本次用户要求，伙伴跟随开始进入设计阶段，仍作为可选插件，与默认绿宝石内容分开。旧 SCOPE/ACTORS 中的“跟随延期”记录是历史范围，本次授权仅覆盖第9、10节的通用能力。

**当前评审结论以第9节为准。第3、7、8节保留为已撤回的职责草案与范围估算，不能直接作为实现清单。** 用户指出上一版将跟随业务过多移入引擎；本稿纠正为先证明公开接口缺口，再补最小通用能力，跟随策略归插件。

## 1. 本次需求

目的：让引擎提供通用角色调度、移动结果和组合事务；后续宝可梦跟随插件通过公开合同实现具体业务。引擎可以调整通用合同，但不能依赖插件 ID、物种 ID、队伍第一位、宝可梦体型或 HM 名称。

交付分为两部分：通用能力扩展，以及使用这些能力的独立插件。谁跟随、能否跟随、何时收回、显示什么素材和互动内容由插件决定。默认绿宝石不自动启用该插件。

## 3. 旧提案：拟补齐的合同（已撤回，保留评审背景）

以下均为设计要求，不是当前可调用 API；最终名称和 schema 在实现前确定。

### A. 角色目标关系与路径跟随

在现有 Actor 控制与导航中增加声明式目标关系：跟随哪个世界实体、保持多少路径距离、选用什么控制政策。第一期支持玩家和 Actor 作为目标；需要拒绝自跟随、循环依赖、已失效目标和相互争用控制权。

宿主持有有界移动轨迹，记录起终点地图/格子/高度、朝向、动作种类、统一时钟与序号。轨迹取自经过规则批准的移动；跟随者仍复检当前地形和占位。正常移动不逐格 teleport，不让插件保存像素插值，也不通过每帧 query/dispatch 自建运动循环。

沿实际路径保持一格左右间距，避免 BFS 在转角抄近路。轨迹缓存要有容量上限、离场/读档清理和追不上时的明确结果。跳崖可引用通用运动描述，不能重放玩家的遇敌、步数奖励或野外行动副作用。

复用已有控制仲裁：剧情控制优先；对话、战斗或其他忙碌状态按声明政策暂停/收起；恢复后重新确认目标及有效路径。第一期不建设任意行为树或多人编队系统。

### B. 关联角色的预约与接触政策

通用关系需要处理前者离格、后者入格的预约时序，以及玩家突然回头、单格通道和目标格被 NPC 占用。可以先选安全的等待行为；若支持交换位置，必须原子预检双方和第三方占位。

只对显式声明的关联实体协调预约，其他 Actor、墙、水面、桥面高度与动态机关仍按原规则验证。不全局开启 ignoreActors/ignoreTerrain，不让非关联对象重叠。

占位、玩家确认互动、自动接触战斗是不同政策。跟随者可响应玩家确认，但插件不为它注册野生遭遇凭证；普通接触不能启动捕捉或重复发奖励。确有合同缺口时补窄的接触分类/过滤，不为此改变全部 Actor。

### C. 场景交接与重新出现

把既有地图连接/warp/传送流程中的交接信息暴露给关联 Actor：源与目标场景、目标合法位置、交接原因、忙碌/遮盖时机与提交结果。属于应用协调，核心不认识 Fly、Dive 或某座房子的 ID。

连续地图保持身份和运动；第一期进出门采用“交接期收起，目标场景就绪后在安全格重新出现”。没有安全格保持收起，不把 Actor 放在玩家/门口触发格/NPC 上，不回滚已经成功的玩家移动。完整跟着走出门的演出可后续补充。

临时收起须释放占位与预约，同时保留关系；恢复只在宿主允许的边界进行，不在 draw/render 内写状态。战斗返回、读档与交通模式变更也走同一生命周期，避免各业务另写恢复监听。

### D. 受控事务与保存

为 Actor 生成/关联/取消/外观及插件记忆提供可组合的受控事务；优先扩展现有意图/状态所有者，不引入绕过 CommandBus 的写口。生成结果应能以当次事务引用关联，后段失败回滚所有参与者，并在成功提交后发布事实。

Actor 领域唯一持有位置、身份和控制关系；插件仅保存 enabled、所选宝可梦 UID 及必要 Actor UID 引用，不复制队伍个体、属性或位置。引擎的目标关系引用世界实体，不绑定宝可梦 UID；宝可梦与 Actor 的业务对应由插件拥有。

轨迹与帧进度为临时数据，读档后重新建立；持久关系保存方式在合同评审时选定，不能同时保存两份权威关系。停用后关系、Actor 和外观须随所属插件暂停；再次启用复检队伍/位置并幂等恢复。

### E. 按需增强方向素材合同

沿用现有图集、姿态和 stride 时钟。若使用独立左右帧，为 SpriteFrame 增加显式镜像描述及合法性检查，默认值兼容现有素材；同步公开类型、采样器和作者文档。此项是任意角色都可使用的表现能力。

现有 w/h 和 offsetX/offsetY 足以先验证尺寸及脚点；先用导入工具规范资源，不为一种图包改造整个资源系统。若后续验证证明锚点/遮挡描述不足，再提出具体合同缺口。

## 4. 插件业务与首期行为

插件放 `src/plugins/pokemon-follow/`，在 catalog 登记，默认关闭。正常玩家入口使用已有详情页扩展入口，提供“设为跟随伙伴／收回”。第一期显式选定一个宝可梦；自动首发选择可作为后续插件设置。

绑定个体 UID，不能绑定队伍下标。换队序不换伙伴；离队、寄存、交易、蛋或濒死按插件政策收起；进化/形态变化重新解析贴图。失败不得留下孤立 Actor，恢复不得生成两个伙伴。

第一期包含：地面步行/跑步、转向、连续地图、进出门的安全交接、暂停与战后恢复、保存/停用/重新启用、开关和切换伙伴。骑车、冲浪、潜水、飞行及暂不支持的移动模式先按插件声明收起，回到支持的模式再恢复。跟随水面/骑乘、多只伙伴、情绪/道具奖励、所有特殊演出另立业务阶段。

## 6. 推荐资源管线

固定修订的只读输入 → 物种/形态/性别/闪光映射清单 → 方向与帧顺序解析 → 本项目水平图集与动画元数据 → resource/actor/appearance 注册 → 插件按个体当前身份选择外观。

- 原始输入保留在独立参考位置，不覆盖 `work/pokeemerald` 或同步 `sources`。
- 手写物种映射、样本选择和来源清单归插件；派生 PNG/元数据写 `generated/plugins/pokemon-follow/`。导入工具先提供只读 `--check` 和覆盖报告。
- 运行时使用本地已注册资源，不每次通过外网拉图。按当前伙伴加载必要图集，避免全部 PNG 同时解码。
- 每项记录资源/图集 ID、帧尺寸、方向序列、显式镜像、时长或 stride、脚点偏移和来源。源调色板可用于离线生成普通/闪光版本，不能直接套战斗调色板推测野外颜色。
- 第一批建议御三家、皮卡丘、拉鲁拉丝、蛇纹熊，再加一个大型样本和一个非对称样本，共约8种。核对地面基线、转角、草丛/建筑遮挡、桥面/倒影和跑步节奏；样本通过后扩到第三世代范围。
- 缺图或必需方向失败时清楚提示并收起该伙伴；不以战斗图、图标或别的物种冒充完成。普通版完成后再逐项核对闪光/性别/形态；降级必须在资源清单中显式声明。

## 7. 旧提案：实施顺序与验收（职责安排已撤回）

1. **合同评审与素材样本**：确定目标关系、移动事实、交接、安全重现、事务和持久所有权；生成样本覆盖与方向检查报告。此阶段不安装玩法。
2. **通用引擎能力**：在现有 Actor/移动/世界应用中补最小合同。用普通 NPC 跟随另一个 NPC 的公开示例验证，证明能力不依赖宝可梦。
3. **最小完整插件**：少量真实素材，玩家入口→选择个体→生成/关联→跟随与换外观→交接→保存恢复→收回。默认内容不新增宝可梦政策分支。
4. **扩充覆盖与验收**：资源扩到所需物种/变体；专项与受影响合同检查；框架收口再整体检查。按既有用户约束，自动工作不通过 Computer Use 操作游戏，真实画面由用户验收。

必须验证：连续走跑与急转/回头；单格通道与第三方占位；不同高度/跳崖；地图连接及出入门；玩家已成功传送但伙伴无落脚格；忙碌暂停与恢复；快速开关/切换；后段失败回滚；伙伴离队/进化/濒死；读档无重复；启用→停用→继续保存→重读→重新启用保留个体 UID 与新进度；坏资源、独立左右帧、reducedMotion 与图层裁切。

验收核心标准：同一能力能服务 NPC/护送类玩法，插件仅通过公开接口完成，移除插件仍可正常玩默认绿宝石；纯合同通过不等于画面已经验收。

## 8. 旧提案：引擎改动范围评估（估算已撤回）

2026-10-07 用户决定先推进引擎能力，产品插件留到后面；本次先核对改动范围。下列数量为代码接线审查后的估算，不是已完成的 diff，也不包括物种资源批量导入。

结论：中等规模、有跨模块生命周期协调的框架增量。预计新增/修改约18–25个运行时代码或公开类型文件；另有约4–6个测试/公开示例文件和4–7份规格/接手文档。许多文件只改端口装配或 schema，不能把触及文件数等同于重写模块数。主要新逻辑预计集中在2–3个小模块：有界运动轨迹、Actor目标关系/跟随控制，以及必要的事务协调辅助；具体拆分按真实所有权确定。

### 可复用且无需重新实现的部分

- `GridMotion` 已有 from/to/start/duration、跨连接地图插值、跳跃与步态；仅轨迹描述确有字段缺口时才改它。
- `FieldSession` 已有 onStart/onProgress/onWarp 与地图切换提交点，可以在现有边界接轨迹和关联角色交接。
- `ActorRepository.objects()` 已排除 hidden 的 Actor，因此隐藏后释放普通占位已有基础；新增工作是清理旧动画预约、控制关系和安全恢复。
- 世界规则、高度、NPC两端预约、Actor持久身份、外观定义与插件停用暂停区继续复用。
- 现有存档校验会构造 ActorRepository；尽量将关系状态归其校验，避免多处复制相同校验逻辑。

各工作组共享文件，不能将每行数量相加。`packs/emerald/application/` 中的改动属于当前宿主的通用能力装配；无需把应用层迁入 engine，也不能将宝可梦业务政策混入这些服务。

### 新确认的难点

1. `NPCSystem.tick()` 目前采用随机初始等待及800–2500ms左右的自主决策间隔。跟随必须有宿主驱动的连续控制节奏，不能只新增一个 npcBehaviors 的 decide 回调；普通自主NPC继续沿原有节奏。
2. `ActorApplication.tick()` 的日程补齐通过 canManageParty 判忙，后者包含玩家移动忙碌。跟随控制必须区分“目标正在走”和“场景被战斗/剧情等占用”，不能复用该条件导致玩家一走跟随者就停。
3. `EventBus.emit()` 当前会同步交付，`StateCheckpoint` 明确不捕获运行时服务。直接把现有 Actor/Appearance 写命令塞进 intent 队列会让失败事务提前泄漏事件或清掉动画缓存；必须采用暂存事实及提交后运行时更新，或可验证的参与者恢复合同。
4. 目标关系带来新的引用：目标 Actor 被删除/属于停用插件时，需要显式取消或暂停关系；现有仅按模板/地图/姿态暂停 Actor 的实现不能直接覆盖该引用。

### 建议三批引擎工作

1. **同场景通用跟随**：关系注册/受控设置与取消、玩家/Actor目标、有界轨迹、走跑/转角、统一移动预约及剧情控制优先。预计触及约10–14个运行时/合同文件。用普通角色素材和公开示例验收，不制作宝可梦产品插件。单格通道回头及失路策略必须能恢复行动，不能靠双方永久等待宣称成功。
2. **交接与持久生命周期**：连续地图、门/传送安全收起与重现、模式政策、忙碌恢复、读档、目标失效与缺插件暂停/恢复。与第一批共享多个文件，必须在正式宣称“引擎已支持插件”前完成。
3. **插件可组合写入与方向素材**：补 Actor/关系/外观可组合事务、结果引用、成功后事件发布、失败不留缓存副作用；补显式左右镜像声明。即使产品插件延期，这些公开能力仍可用最小测试插件/作者示例证明。

首批不扩大到多角色编队、任意控制器框架、自动执行HM、全世界离屏模拟、物种贴图导入或详情页产品入口。整轮引擎工作完成后，产品插件可以在现成合同上继续，不需要重新修改引擎来识别宝可梦业务。

本次只增加范围评估文档；没有修改运行时代码，没有因范围审查重跑游戏测试。前述2项代表例证据仍仅覆盖其原有行为。

## 9. 当前规范复审：业务策略归插件，只补经证明的通用缺口

用户质疑成立：旧提案虽未按宝可梦/插件ID增加分支，但“改名为Actor跟随”及“再举一个NPC跟随例子”不足以证明职责分配合理。旧提案将谁跟随谁、路径历史、保持距离、收起/重现等策略直接交给引擎，扩大了核心职责。18–25个运行时文件的估算随旧职责划分撤回，不能继续作为执行预算。

规范依据：[AUTHORING](../development/AUTHORING.md)第17、38行，必要的新通用规则/生命周期先给缺口合同，变化的政策注册为内容，无通用需求不加空抽象；[SCOPE](SCOPE.md)第29、39行，复用已有合同，只对不能表达的输入/结果/生命周期提出框架任务；[ACTORS](../engine/actors/ACTORS.md)明确允许插件行为使用data、感知、goal和移动意图，框架持有身份、位置、占位和运动执行。

### 纠正后的所有权

| 职责 | 所有者 |
| --- | --- |
| 谁跟随谁、间距、沿原路/寻路策略、何时等待或放弃 | 插件注册的行为政策 |
| 为跟随目的保留的有界路线历史与业务关系 | 插件自有临时记忆或模板schema的行为数据；不复制领域权威位置 |
| 是否在某种交通/场景条件收起、何时请求重新出现 | 插件政策 |
| 宝可梦UID绑定、资格、素材解析、互动与菜单 | 宝可梦跟随插件 |
| 身份、权威位置/高度、合法运动执行、插值与预约 | 现有Actor/世界/移动领域 |
| 行为的受控执行节奏、冻结感知、生命周期事实、受控写入 | 现有宿主合同；仅在表达不足时扩展 |
| 存档与缺插件保护 | 现有领域与插件记忆合同；新增字段时才补引用校验 |

纯decide回调可读取冻结输入，返回下一步移动及行为记忆；不能修改世界或在其中dispatch。宿主持有运动时钟和执行结果，插件不能另建帧循环。路线政策与运动执行因此保持分离。

### 当前候选缺口及其证明要求

1. **可声明的行为调度节奏**：现有NPC统一带随机等待，影响连续移动。先用公开行为示例证明需要连续巡逻/逐步响应；若确实不能表达，在既有行为注册上补有界调度配置。引擎决定安全调用时机，插件决定要走哪一步；不新增专属follow控制器。
2. **可消费的移动与场景事实**：现有field-step只有目的位置。先证明该信息确实不足，并检查现有回调/公开查询能否组合；必要时补来源、结果、时序或交接原因。引擎公布事实，不建立跟随路线数据库，也不决定进门收回伙伴。
3. **Actor受控写入的可组合性**：已有spawn/update/remove不能直接在插件action中组合。用“生成普通Actor并初始化插件记忆，后段失败”的公开用例证明缺口；再补窄意图和事务引用、提交后事件/缓存协调。无需先新增完整通用事务参与者框架。
4. **移动预约表达能力**：先用现有移动和安全等待证明能否满足连续行为与回头恢复。只有现有公开合同无法表达合法协同移动时才补机械性的预检/提交能力；没有证据前不新增关联组穿行、专属交换或碰撞豁免。
5. **方向帧镜像声明**：已有固定右向镜像是明确素材表达限制。用独立左右帧的普通角色夹具验证，再补显式镜像数据；不与跟随功能绑定。

跨地图安全落点查询、行为结果反馈及读档就绪边界也须先对照现有合同；在实际公开示例失败前，它们是待审查项，不能先写成必改模块。

### 下一步执行方式

以现有接口写最小公开夹具（连续巡逻、Actor创建失败回滚、独立左右帧），逐项记录“现有接口输入→实际失败/受限→最小合同→成功和失败验收”。这属于框架验证，不制作宝可梦产品插件。

先确定并实现已证明的最小缺口；用两类不同的非跟随用例证明合同不携带伙伴业务政策。随后重新估算文件数。跟随算法、业务关系和伙伴恢复策略不纳入引擎扩展；若插件开发时再暴露缺口，仍按同样流程单独评审。
