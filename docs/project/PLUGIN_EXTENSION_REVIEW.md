# 通用插件扩展评审：行动组合与战斗语义

2026-10-06，**方案待共同评审，未实施战斗插件接口变更**。Z招式和Mega只作为检验案例；交付目标是插件可以组合规则，不能在核心增加机制名称或物种ID分支，也不在默认Gen3包安装现代玩法。

## 当前结论与代码证据

现有框架可以做“限次替换招式”与“临时形态切换”的简化玩法，尚不能仅靠公开插件API准确组合完整的现代战斗机制。缺口主要在行动和时序合同，资源素材/威力表则属于内容。

| 通用能力 | 已有 | 真实限制及证据 |
| --- | --- | --- |
| 一次行动替换 | `battleAugments`声明资格、替换招式白名单、原槽PP、库存费用、battle/alliance/controller/creature限次；取消释放预留、失败恢复 | 只能返回完整招式ID，拒绝多回合替换；不提供原招式属性继承与受限属性投影。见[augments.js](../../src/engine/battle/augments.js)、[合同](../engine/battle/AUGMENTS.md) |
| 形态投影 | 非HP能力、属性、特性、图片、持有物条件、每控制者一次、换人/倒下/结束清理 | `kind:form`在选择时立即激活、发事件并调用`traits.enter`，取消后不会恢复这项已提交选择。见[battle.js](../../src/engine/battle.js)、[形态服务](../../src/engine/creatures/forms.js) |
| 排序与阶段 | 优先级、有效速度、规则钩子、稳定平局随机数 | 排序直接读取当前投影，缺少“所有行动确认后、排序前”的受控附加行动提交合同，也缺少选择时与生效时分别取值的政策。见[round.js](../../src/engine/battle/round.js) |
| 资格 | 招式增强有只读`requires`；形态有固定物种/持有物条件 | 形态没有通用资格回调；增强context的actor大部分仍是本体，只有types来自有效形态，无法一致查询有效能力/招式/形态。训练者能力条件也没有声明的战斗投影端口 |
| 限次与资源 | 增强有共享key的预留/账本/检查点；形态有`used`集合 | 两条生命周期分离，不能声明跨机制互斥或共享额度。不是说所有现代机制必须共用一次额度，而是框架要让规则包决定共享与独立 |
| 命中与伤害 | 现有命中、免疫、伤害修饰阶段；Gen3是默认政策 | 保护在[moves.js](../../src/engine/battle/moves.js)直接拒绝；跳过整个hit-check会连免疫/隐藏目标检查一起跳过。物理/特殊在[model.js](../../src/engine/model.js)仍按属性决定，无法声明每次招式类别 |
| 效果组合 | 已注册op、多个效果阶段、状态生命周期 | 纯primary与伤害阶段互斥，不能把通用“本次行动额外效果”直接与保留原行动语义组合。插件不能注册任意新op，不应通过导入核心或任意回调绕过所有者 |
| UI、AI与演出 | 战斗区域可替换/追加，原生句柄；合法增强候选；语义事件演出 | UI不是主要阻塞。主机缺少统一的附加选择/取消/预览结果，插件UI自行拼写会偏离真实可用性；AI也应消费同一候选合同 |

这里不把HP缩放、全局永久限次、任意行动类型或动态卸载列为Mega/Z必须修复项：前两例不证明这些需求。已有特性投影、形态清理、PP回滚、UI槽、表现注册也不重复建设。

## 建议方案：增量扩展已有所有者

以下是**拟议合同方向，名称/字段不属于当前可调用API**。保留现有Action、Round、CreatureForms、MoveExecutor、Checkpoint及UI/策略端口；不增加第二套战斗内核。

### 1. 行动附加选择与受控提交点

在现有move选择中携带一个或多个已注册的附加项引用，而不是先执行免费的独立命令。候选查询返回资格、不可用原因、目标模式、费用、额度以及生效点；只传注册ID/合法参数，不能由UI发送原始属性覆盖或内部计划。

宿主将选择编译成只读执行计划，并绑定actor UID、席位、源招式槽和本轮决策修订。再次选择替换原计划；单席位取消释放自己的预留，全轮取消清空全部预留；未确认不改形态/PP/库存，不发已生效事件。多席位与AI在同一个决策表中预留，不能分别承诺同一份额度。

初轮只开放三个固定提交点：`beforeOrder`（排序前）、`beforeAction`（该行动执行前）、`moveStart`（已能发动本次招式时）。不能自行插入任意阶段或改变Round关键顺序。允许的效果和费用提交点由注册器验证，非法组合启动拒绝。

这让“先切换有效状态，再排序/行动”与“只增强本次招式”共享选择合同，却保持自己的生效条件。无法行动时是否仍发生前置形态切换，取决于其提交点；不能沿用一条“睡眠就统一不消费”的隐藏假设。

### 2. 通用资格与额度预留

资格context同时提供基础身份和完整有效投影：base/effective creature、sourceMove/当前招式槽、controller/alliance、受声明的controller capabilities、天气及必要战场状态。全部冻结、同步、可重复求值；只读回调不能扣费、取随机数或提交命令。控制者能力由应用/规则包建立受校验投影，不开放整份世界存档。

形态和招式附加项都引用同一个战斗所有者管理的`scope + subject + key`额度池，支持独立key与显式共享key、容量、互斥组和预留。额度服务负责reserve/release/commit/checkpoint，形态记录继续由CreatureForms拥有。装备条件默认只检查，不消耗；库存费用由Inventory负责；原槽PP仍由MoveExecutor支付，不归插件store。

每个提交点复验UID、资格、费用和引用，不能退而使用另一招式或换到另一只精灵。额度消耗发生在对应的真实生效提交；开始后未命中/被挡不退回，未开始则释放。内部异常恢复领域、账本、待选、随机数和未公开事件，失败报告不能伪造成功。

### 3. 有边界的招式派生与判定政策

保留已注册替换招式白名单，追加受校验的“从源招式派生”计划，初轮只允许必要字段：威力、属性、类别、目标、命中政策、优先级来源及效果定义引用。每个字段区分继承、固定值或受限纯查询；不存在任意函数改战斗对象、任意JSON合并或动态注册招式。

伤害类别变成声明政策：默认继续Gen3按属性选择，独立规则包才启用按招式/计划选择。排序优先级与招式判定所见的优先级分别取自明确政策，避免“替换为另一招式”顺带改变本回合行动顺序。

将保护判定独立为通用防御交互结果，允许block/pass/scaledDamage等有限结果；免疫、隐藏目标、准确率各有独立政策。缩放必须进入正常伤害管线及其取整位置，不能靠`bypassHitChecks`跳过全部检查，也不能在UI直接扣HP。

额外效果通过已注册效果/op与生命周期组合，明确是在原行动前/后、失败时是否仍生效、按行动一次还是按目标重复。保留原招式的蓄力/硬直等行为须显式选择兼容的策略，不能直接解除当前多回合替换禁令。首轮遇到现有op表达不了的语义再补窄op，不一次开放任意自定义执行函数。

### 4. 有效状态切换生命周期

复用CreatureForms投影，增加通用资格及明确的transition提交事实。特性变化区分“旧来源解除→新来源附着→状态切换触发”与“实体入场”，不能一律重播全部entry逻辑。同一只精灵的形态、临时能力覆盖、压制状态及恢复须有明确优先级，避免两个插件互相覆盖。

形态记录、来源UID、持续范围、离场/倒下/结束策略仍由同一服务持有；换人恢复能力来源但不恢复已用额度。世界持续状态才走现有保存合同；战斗临时状态不进入存档。表现按提交事实播放，动画失败不会重新执行规则或支付费用。

### 5. 组合验收与推进顺序

先做行动附加选择、固定提交点和共享额度，再做完整资格投影/状态切换，最后补招式派生与防御交互。每一阶段公开类型、注册校验、查询、命令、失败恢复及一个真实组合例一起交付，不能只列API名称或单测一个类。

用三个没有现代机制专名的最小插件夹具验收：

- 战术姿态：随本轮招式选择，排序前变能力/特性；取消完全无副作用，重新选择正确释放，换人/结束恢复，双席位争用只允许一方。
- 蓄能攻击：继承原招式类别/优先级、派生威力，原槽PP一次扣除；普通防御与部分减伤独立，免疫仍拒绝；睡眠/目标离场/后段异常结果明确。
- 支援附加效果：原行动保留并附加注册效果，按行动仅一次，失败政策明确；AI与UI查询/取消消费相同合同。

Z/Mega只作为最终覆盖检查，规则包另行确定第六/第七世代行为和数据；通用例通过不等于完整现代机制已完成。默认Gen3原结果不得改变，也不恢复已删除产品玩法。

## 供这次共同评审的取舍

建议**扩展现有battleAugments与行动计划**，复用形态服务，避免新建一个可以包办所有领域的插件事件总线。首轮限制在招式附加项，任意新增行动类型暂不开放。新查询可先并行提供；既有即时`kind:form`作为明确的即时形态操作保留，新组合能力不复用它的选择时提交行为，避免静默改变已有插件。

核心必须掌握阶段顺序、来源身份、资源支付及回滚；插件掌握资格定义、形态/招式内容、额度key与声明政策。`forms.used`向统一额度迁移时保持现有oncePerController语义，并针对二者并存/取消/失败补证明。额度池key要按所有者命名空间校验，跨插件共享需显式声明依赖/授权，不允许偶然拼出同一key抢占额度。

拟议字段、迁移方式和首轮三个提交点需我们对齐后再实现。本轮只修复目录/字段重复/跑步，战斗接口、战斗规则与默认内容未修改。
